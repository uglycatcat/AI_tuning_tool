# 背景
1. 该项目只在开发者本地运行，前端作为一种交互手段。
2. 美术风格要求黑白高级风
# 需求
分为两个模式，一个是虚拟PID测试模式，一个是串口调试模式
## 1. 有虚拟PID测试功能，用来调试tuning_tool
该功能暂时作为一个独立功能。
有开始，暂停，重启
目标曲线有三角波，正弦波两种类型。两种信号都有周期，振幅，偏移参数。
当前曲线有PID三个可调参数

### 实现虚拟PID情况下与tuning tool的联动，借助tuning tool调整参数
在虚拟PID内添加一个标识控件，默认为空，表示不接入tuning_tool，点击后翻转为true，表示接入。再次点击可以关闭。但是注意，这个控件被改变后，只在下一次点击重启生效。
重启时如果发现该控件为true那么接入tuning tool。
流程如下，接入后，正常进行计算和图像滚动，但是与此同时以固定频率和总采样时长按照tuning_tool的要求采集相关数据，输出csv文件。然后发送给tuning_tool，与此同时，prompt_concat拼接后的prompt原本输出到output.log的内容现在输出到右上角的prompt文本框中，每次response_parser输出给outpot2.log文件的内容现在输出给右下角的response文本框。
并且需要把response_parser解析出来的pid返回到当前虚拟pid的pid值，从而实现让ai读取当前数据来调整参数。
然后再重复下一轮采集csv数据
（当前tuning_tool测试阶段使用json文件，需要你更改为csv文件）
（需要打开当前所有的边界性限制来进行测试）
目前是测试阶段人为规定进行三轮循环

## 2. 简单的串口调试助手，用来实际接入串口进行调试
不需要完整的调试助手，只需包含以下功能
无需显示实际接受的数据文本或者下发的数据文本，包装成简单的ui即可

有端口号，波特率选项（默认端口号为tty/USB0,默认波特率为1000000）只有这两个串口配置参数有UI控件
其他参数配置到根目录的config文件里面，包括数据流空默认None，校验位默认None，数据位数8,停止位数1，DTR默认关，RTS默认关

点击启动后下发，类似于虚拟pid有周期 振幅 偏置 可调参数
"debug_pid_ai_tuning start [period,amplitude,offset]"
接下来会接收数据
接收到的数据流字符串格式下是这样，需要检验格式才录入，
"pid_tuning_param[timestamp,setpoint,input,pwm,error,p,i,d]"
解析失败则显示“数据解析失败”
没有接收到数据显示“没有收到数据”
你无需显示接收到的完整数据
其中error，setpoint，input绘制到图像中类似虚拟pid即可

暂停画面仅停止图像刷新；后台仍持续接收并解析串口数据，下位机继续工作

和虚拟pid类似可以手动调整pid
下发指令为
"set_pid[p,i,d]"
只需像虚拟pid一样留出可修改的三个文本，然后用户修改就下发串口指令

有关闭按键
点关闭后停止下位机
"debug_pid_ai_tuning stop"
之后下位机不在发消息

### 串口模式接入 tuning_tool（与虚拟 PID 对齐）
- 勾选「接入 tuning_tool」后，仅在下次点击**重启**时生效（与 §1 虚拟 PID 规则一致）；**重启**会清空曲线与调参轮次状态，不会自动再次下发 `start`，需用户再点**启动**。
- 生效后，在收到合法样本流时按根目录 config 中 `AI_TUNING_*`（经 `/api/tuning/ui-settings`）进行固定间隔采样、满一轮时长后调用与虚拟模式相同的 `/api/debug/virtual-round`；`plant_profile` 为 `hardware_step`，CSV 与 output2 日志落在 `web_tool/runtime/serial_rounds/`。
- Prompt / Response 文本框与虚拟模式共用分页逻辑；解析出的 PID 写回 `sp-p/i/d` 并立即尝试下发 `set_pid[p,i,d]`。

### 串口模式操作流程大修改
当前已经成功完成测试并且正常调整参数，打通了工作管线。接下来我们需要重新开始处理整个前端的操作流程和代码逻辑
（
以下默认：
一个按键变灰色表示该按键不可用
程序运行的本地称为上位机，串口另一端的设备称为下位机
接入tuning模式称为ai调参模式，不接入的情况称为手动调参模式
）
1. 当前UI界面调整如下：
    1. 把跟踪曲线的三个参数和PID三个参数放在同一行
    2. 切换到串口模式的界面后，
    下方的按键行应当有
    “连接设备” 连接串口与下位机建立通信
    “断开设备” 断开串口（不用发送stop等其他指令，只断开与下位机的通信）
    “启动设备” 发送PID跟踪指令及参数到下位机
    “重启设备” 发送stop停止设备指令，重置图表，缓存等，
    “停止设备” 发送stop指令，下位机会停止发送消息，图像停止刷新
    “暂停画面” 暂停图像刷新，但是仍然正常接收和处理数据
    3. 把“刷新列表”按键文本改为”刷新串口列表“
2. 逻辑调整（按照用户使用逻辑）如下：
    1. 每次切换到串口模式时是默认手动调参模式，除此之外每次点击重启时依靠标志位来确定接下来是否接入ai调参，同时每一次重启都会完全重置。注意之前发现，如果从ai模式突然调回手动模式，飞行中的response仍有可能改变手动模式的pid以及prompt和response的内容，这bug需要解决，只需要确认在手动调参模式下不收ai模式遗留的消息即可。
    2. 在手动调参模式下，用户会先检查是否检测到串口，然后点击“连接设备”，连接成功后，“连接设备”不可用，连接失败则报文显示“连接失败”，之后用户调整跟踪目标曲线的相关参数，然后点击启动设备，发送PID跟踪指令，下位机会按照参数创建目标曲线然后开始跟踪（如果下位机的上一次曲线没有停止也没关系，下位机会按照新参数继续，同时向本地发送相关信息，解析失败则显示“数据解析失败”。没有接收到数据显示“没有收到数据”。数据正常解析后，“启动设备”按键不可用。之后的流程正常，图像显示后。
    用户接下来按下 “断开设备” 则直接断开，不用管是否停止下位机，此时没有消息收到，画面应该停止，然后“连接设备”和“启动设备”恢复可用
    用户接下来按下 ”暂停画面“ 则”暂停画面“键变为”继续画面“键，暂停后后台正常接收和处理数据，但是图像不发生变化，点击继续后才更新新数据
    用户接下来点击 ”停止设备“ 则发送stop指令。下位机会停止数据的发送和跟踪。上位机画面会停止在最后的画面。“启动设备”恢复可用。
    用户在任何时候可以点击 “重启设备” 除了串口不断开以外，发送stop命令，并且清空所有内容。点击重启设备后，“启动设备”恢复可用。
    用户可以通过修改pid参数，在修改后，触发向下位机发送pid参数的命令。
    用户可以通过修改目标曲线参数，在修改后，触发向下位机发送目标曲线参数的命令。
    3. 在ai调参模式下，是相同的操作逻辑。启动后开始向ai询问和回调修改pid，暂停画面不会影响任何后台修改和询问，仅仅只是画面不继续刷新。注意停止设备时，如果已经发送了prompt并不会打断询问，可以正常更新参数（更新pid参数和目标曲线参数都正常），类似于虚拟PID情况下的“暂停”。但是如果点击了重启，那么需要注意上一轮如果遗留了飞行中的prompt或者response就不处理了。
    4. 接收来自串口的信息时，需要注意，串口端发送的消息至少为100Hz，最高为1000Hz，需要有自适应方案，同时保证画面的流畅和采集数据的采样有意义和可靠。

## 3. 有PID图像，方便开发者可视化调参效果（虚拟的或者从串口读到的）
- 横轴为时间，默认 **10s** 滚动窗口；按当前模式显示数据源（虚拟仿真 / 串口接入后的数据流）。
- **三条曲线**：目标位置、实际位置、**位置误差** \(e=r-y\)。
- **双纵轴**：左侧为位置量纲（目标、实际）；右侧为**误差**量纲（误差曲线），右轴刻度仅反映 \(e\)。
- 曲线区域上方有**文本统计**（当前误差、窗内平均绝对误差、最大绝对误差、样本点数等），便于快速判断跟踪质量。

## 4. 有文本框可以显示当前发给ai的request的prompt和收到的response给开发者来确认流程是否正确

### 虚拟PID接入tuning_tool的情况

#### prompt框
该文本框会累积显示这一次接入tuning_tool之后，每一次给ai端发送的文本，并且不能被用户修改，只能展示内容。
因为会产生多次prompt，应该有页数标志，可以通过页数直达当次的文本。
每次切换模式或者重启的时候清空

#### response框
该文本框会累积显示这一次接入tuning_tool之后，每一次ai回复后tuning_tool的parser处理后输出的文本，并且不能被用户修改，只能展示内容。
因为会产生多次response，应该有页数标志，可以通过页数直达当次的文本。
每次切换模式或者重启的时候清空
